# 宮下愛：第3次登場，而不是第3次及以后

## 修正结果

先用实际卡牌复现3项失败：第4次、第5次仍抽到5张；第3次登场时被普通替换的来源则漏触发。
新登记现在区分事件发生与结算：只在第3次登场触发；已经待机后不因来源离场或出现第4次登场而取消。
手牌数量不在触发时锁定，结算时只补当前不足5张的部分。

这是既有entry的准确度修复，**登记仍899/1212（74.17%），313 manual**，不升级 reviewed。

## 可核对的状态结果

| 场景 | 实际结果 |
|---|---|
| 来源已在场，第1 / 2 / 4 / 5次外部登場 | 不触发，不补牌 |
| 来源已在场，第3次登场到空区域 | 触发1次，当前1张手牌补至5张 |
| 来源自身在第3次 / 第4次登场 | 第3次补到5；第4次不触发；自身实际支付cost15 |
| 来源在第3次登场时被普通替换 | 清理前保留待机能力，进入控室后仍补到5 |
| 来源作为Baton费用先离场 | 不观察后续第3次登场，不补牌 |
| 第3次触发后先处理另一个抽2能力 | 结算时手牌3张，只再抽2，不按先前1张重复抽4 |
| 第3次触发后先处理另一个让来源离场的能力 | 来源已进控室，原待机仍结算 |
| 第3次触发后，父能力先效果登场另一Member，计数变4 | 原待机快照仍为3，结算1次；第4次不另触发 |
| 有界效果登场到空区域 / 覆盖来源区域 | 同样按第3次入队，完整来源的无关Live段不误挡区域 |
| 两个来源副本同在场观察第3次 | 各触发1次；先补到5后，后一个不重复抽到更多 |
| 结算时已有5 / 7张手牌 | 不抽、不弃，不误当作“调整至5张” |
| 第2段Live开始时计数1 / 2 / 3 / 4 | 分别拒绝 / +1分 / +1分 / +1分，保持“2回以上” |

先处理“补到5”后再处理另外抽2也可能得到7张，这是合法的顺序差异，不是重复触发。
三种AI的测试接受原生LegalAction选择的合法顺序，不强制伪造同一种手牌结果。

## 显式新条件与旧Replay

```json
{"trigger_member_entry_count_exact": 3, "trigger_source_zone": "stage"}
```

只有单一、强制、无费用/选择/持续期的补手牌观察者可使用这对条件。
引擎在真实触发时保存计数和来源当时的Stage资格；缺失或错误快照会拒绝，不猜测当前场面。
不读取对手手牌，不向UI下发新选择，不新增MatchState字段、HTTP端点或SQLite migration。

旧effect snapshot仍有 `own_member_entered_count_this_turn_at_least` / `source_zone`，
保留其历史行为和事件；新旧actual SQLite Replay均核对最终state、完整events和state hash。
另以两步SQLite Action核对“第3次待机 → 第4次效果登场 → 原能力结算”的快照保存。
候选原来的人工 `once_per_turn` 草稿与registry不一致，本轮统一为none：精确第3次事件本身就限定时点，
不捏造卡文未写的次数标签。第二段、revision、原文hash和登记状态不变；manifest更新registry hash。
