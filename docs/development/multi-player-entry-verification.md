## 结论

修正 `PL!-pb1-018:1` 的多人登场：双方先按 AP / NAP 顺序选择卡与空区域，全部选择完成后，
才同时以 Wait 登场。两边都放置完成后检测登場及己方登場观察者，父技能结束后再结算。

## 实际状态断言

受控目标带“登場抽1”，己方场上观察者带“己方 Member 登場抽1”。这些是测试 fixture，
不声称卡图中的原卡持有这些抽牌能力。

| 步骤 | 修正前 | 新 snapshot |
|---|---|---|
| 第一人选择卡与区域 | 立即移动；未产生登場触发 | 卡仍在控室，区域、手牌和登場次数不变 |
| 第二人完成选择 | 第二人移动，双方均漏抽牌 | 双方统一移动，Wait / 正面，进入次数各 +1 |
| 两项受控抽牌 | 每人实际 0，期望 2 | 每人实际 +2，所有移动先于任何抽牌 |
| 效果拥有者不是 AP | 拥有者先选 | AP 先选，后续待处理按 AP / NAP 顺序 |
| 条件要求双方场上共 4 人 | 无法验证正确登場链 | 两次入场后再检测，双方登場抽牌条件成立 |
| 最终选择前首个目标变非法 | 无统一校验 | 校验双方全部选择后才移动；本次 Action 原子回滚 |
| 任一方无合法目标 | 不应凭空选择 | 无目标确认 / 跳过该方；另一方仍正常登場 |

新增 `tests/test_multi_player_entry.py` 的 **26 项**测试覆盖非法卡、占用区域、变更费用、
错误操作者、过期 revision、可选拒绝、无目标、共同场面条件、实际抽牌与处理顺序。
另含新旧 snapshot 的真实 runtime SQLite Replay、部分选择序列化恢复、双方公开视角，
以及三种 Simple AI 的原生选择和隐藏手牌身份不变性。UI 增加 2 项组件测试。

## UI 与兼容性

修正多人选择面板从空 inspected 列表取候选、错误提交数组的问题。现在显示当前选择玩家、
候选卡、日文原文和区域按钮；未同时完成卡与区域选择时不能确认。提交现有 API 的
`selected_card_instance_id` / `slot`，换玩家时清空上一人的 UI 选择。

只有新登记使用 `choice.deployment_policy=simultaneous_member_area_entry` 和显式 `wait`。
缺省策略不写入旧序列化，保留旧快照立即放置 / 漏触发的历史行为与 hash，避免伪造 Replay 一致性。
新策略只允许单个控室 Member、明确朝向且没有后续 operation；不声称支持任意多阶段 DSL。
没有 Card Schema、runtime SQLite schema 或 HTTP 契约变更。
